2. Product in plain words

PeopleOS is an internal HRMS. One web app: every employee gets self-service (Me). Managers, HR, IT, and Security see extra sidebar sections based on roles.

Mental model: one login → role-based sidebar → APIs under /api/v1/… → Postgres.

Live today (safe to demo)

  • Auth, RBAC, forgot password
  • Leave apply / approve
  • Attendance (web + biometric path)
  • HR employees / org / documents
  • Payslip PDF upload/download
  • IT assets + My Assets
  • Helpdesk (employee create)
  • In-app notifications

Not the focus yet

  • Full Indian payroll engine
  • PMS / OKR / LMS / expenses
  • Full workflow engine
  • Some Admin screens are UI-only
  • Mobile beyond attendance is thin

Non-technical product story for stakeholders: product guide HTML.

5. Architecture (big picture)

Browser (Vite React) │ JWT in localStorage ▼ NestJS API (/api/v1/...) │ Prisma Client ▼ PostgreSQL (Docker :5440) Side: Mailpit for OTP email (SMTP :1025) Side: eSSL iClock devices → attendance ADMS endpoints
  • Modular monolith — one API process, feature modules (auth, leave, attendance, assets…).
  • Single tenant runtime today; schema still has tenantId.
  • PeopleOS is attendance SoR — punches are not synced from greytHR.
  • Payslips = PDF files HR uploads; not a payroll calculator.

6. Auth & RBAC (must understand)

Login flow

Login page → POST /api/v1/auth/login → access + refresh tokens stored → AuthContext loads user → land on /ess → sidebar from roles.
TopicWhere to look
Web tokens / API clientapps/web/src/lib/api.ts
Auth provider / login stateapps/web/src/auth/AuthContext.tsx
Route guardsProtectedRoute.tsx, App.tsx RoleOutlet
Sidebar by roleapps/web/src/layout/appNav.ts
Role → permission matrixapps/api/src/rbac/role-matrix.ts
Auth moduleapps/api/src/auth/

Two layers: (1) route/nav roles (MANAGER, HR_EXEC, …) control what UI you see; (2) permission codes (leave.approve, assets.manage, …) guard APIs.

Roles not seeded as logins: HR_HEAD, LEADERSHIP_READ, FINANCE_READ — assign via Admin → Users & Roles (/admin/roles).

9. Backend map (API)

  • Feature folder: *.module.ts, *.controller.ts, *.service.ts.
  • Global config via Nest ConfigModule; local secrets in apps/api/.env (gitignored — start from .env.example).
  • Permissions checked with guards tied to role-matrix.ts.
  • Health: GET /api/v1/health.
  • Throttling enabled globally (see ThrottlerModule in app.module.ts).

Example end-to-end: leave approve

  1. Employee UI: ess/pages/EssLeavePage.tsx → leave API.
  2. API: apps/api/src/leave/ creates LeaveRequest, updates balances.
  3. Manager UI: ManagerInboxPage / team leave → decide.
  4. Notification emitted → bell / notifications page.

Walk this path live in KT — it teaches auth, RBAC, Prisma, and UI wiring in one story.

10. Live demo path (20 minutes)

  1. Employee — apply leave, open attendance, open My Assets.
  2. Manager — Inbox → approve leave.
  3. HR — Employees / Leave Admin / Document Center.
  4. IT — Asset dashboard → register → tickets.
  5. Admin — Users & Roles → assign LEADERSHIP_READ → show /exec.

Forgot password: request OTP → open Mailpit → reset. Good test of mail + auth.

11. Gotchas for new developers

  • Mock vs Live: Some Home widgets, Manager overview/directory, Admin audit/jobs/settings still use mock/static data. Check docs/34-feature-catalog.md before assuming Postgres.
  • Helpdesk manage: company APIs exist; dedicated HR ticket screen is incomplete.
  • Salary extras: YTD / loans style panels can be sample UI — PDFs are the Live payslip path.
  • Prisma client drift: after pulling schema changes, always prisma generate (and migrate).
  • Vercel: hosts the Vite web app; API/DB may be separate. Local Docker is the reliable full stack for development.
  • No portal switcher: role sections appear in one sidebar (decision D-028).
